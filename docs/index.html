RDF Triple Store Tracker

An open, evidence-based survey of RDF triple stores. It compares fifteen: five of the most widely used, plus QLever and RDF-HDT for very large and read-only data, AllegroGraph for partitioned commercial knowledge graphs, MarkLogic Server, a document database with a triple index, RDFox for in-memory incremental reasoning, Blazegraph and Eclipse RDF4J from the open-source Java lineage, Oxigraph, a Rust store you can embed or run as a server, sparq, an experimental pre-1.0 Rust engine, and MillenniumDB, a research engine for RDF and property graphs that its README says is not production ready. For each one it covers what standards it implements, how it reasons, how it scales, and what you need to pay to run it.

What the survey found

Seven patterns stand out once every store is lined up against the same checklist.

SPARQL 1.1 is the baseline. RDF 1.2 is not.

Every engine here answers SPARQL 1.1 queries, and all of them accept updates except plain HDT files, which are read-only. Jena TDB2 and Eclipse RDF4J ship RDF 1.2 / SPARQL 1.2 triple terms in a stable release. RDF4J 6.0 stores triple terms in its memory, native and LMDB databases and replaced its earlier RDF-star APIs. Oxigraph 0.5.11 exposes preliminary RDF 1.2 and SPARQL 1.2 draft support behind the rdf-12 feature. The released command-line, Python and JavaScript builds enable that feature; the Rust library does not. The 0.5 line dropped the RDF-star feature and migrates an existing database the first time it is opened. sparq 0.1.6 stores and queries RDF 1.2 triple terms in an experimental pre-1.0 release. Its query guide says that path is not full SPARQL 1.2 conformance, and the tree has no RDF-star mode. Virtuoso has RDF 1.2 in development and QLever has an open issue for it. GraphDB and Stardog still use the older RDF-star model. AllegroGraph has opt-in RDF-star that Franz still marks experimental; its product page names SPARQL 1.2, and the RDF-star document does not describe triple terms. RDFox 7.7 documents SPARQL 1.1 Query with two exceptions, no DESCRIBE and no one-argument BNODE, and its documentation describes neither RDF-star nor RDF 1.2. MarkLogic Server 12.1 documents SPARQL 1.1, including SELECT, ASK, CONSTRUCT and DESCRIBE. The 12 semantics guide does not document RDF-star, RDF 1.2, or SERVICE. SPARQL Update changes managed triples only. MillenniumDB 1.0.0 describes its SPARQL 1.1 support as fairly complete. Named graphs, FROM and GRAPH are unsupported, and SPARQL Update is only INSERT DATA and DELETE DATA. The engine does implement SERVICE. It documents neither RDF-star nor RDF 1.2. Neptune and Blazegraph have neither.

The biggest public endpoints are moving to QLever.

UniProt moved its endpoint from Virtuoso to QLever in June 2025. A year later, Wikimedia chose QLever to replace Blazegraph behind the Wikidata Query Service, with migration due by mid-2027. A university-built open-source engine now anchors two of the largest public SPARQL services.

Reasoning splits into different philosophies.

GraphDB materialises inferences at commit and retracts them incrementally. Blazegraph materialises RDFS+ and maintains it as data changes, though not in quads mode. Stardog rewrites queries at run time. AllegroGraph answers with RDFS++ at query time and can materialise an OWL 2 RL subset when the data is static. Virtuoso applies lightweight RDFS rules at query time, and Jena and RDF4J run rule engines in memory. RDFox materialises an extended Datalog, translates OWL 2 RL and SWRL into those rules, and maintains the closure as facts and rules change. MarkLogic Server applies rules when the query runs. The shipped sets are an optimized RDFS ruleset, RDFS-Plus and OWL Horst, and custom rules are allowed. It does not materialise the closure. sparq materialises RDFS, OWL 2 RL and Notation3 in a crate the default workspace build includes. OWL 2 EL and an experimental OWL 2 QL rewriter are separate opt-in crates. Neptune, QLever, RDF-HDT, Oxigraph and MillenniumDB have no built-in inference.

Scale-out means replicas, or one very big server.

AllegroGraph FedShard and Blazegraph both partition writes. FedShard places triples by a key, runs each query on every shard, and keeps shared ontologies in knowledge bases every shard can see. A shard cannot see another shard's instance data, so the partition has to match the questions you ask. Blazegraph's archived release documents a different split: each data service buffers writes in a journal and migrates them onto read-only index segments. MarkLogic Server partitions documents, including the documents that hold managed triples, into forests across hosts. A query runs across that cluster. A local-disk failover replica is a copy of one forest, not a second way of splitting the data. Everywhere else, a cluster means a full copy on every node: GraphDB, Stardog, Virtuoso Enterprise and Neptune buy read throughput and availability that way, and capacity stays on one machine. QLever takes the single-machine route and serves Wikidata-scale data from one server. Virtuoso's elastic cluster belongs to its older 7.x commercial line. Oxigraph is a single store. Its architecture notes say a distributed database is not a goal of the project. sparq is a single store as well. Its Helm chart pins one replica, and the chart says the writable store is unreplicated. RDFox is also one in-memory copy. Its high-availability group is further copies of that same store, sharing a directory, not a partition of it. MillenniumDB is one server process on one database directory. The wiki and the source describe no replication and no partitioning.

High availability is where the money is.

High availability is an enterprise licence for GraphDB, Stardog and Virtuoso, an external add-on for Jena (RDF Delta), or a hand-off to AWS (Neptune). AllegroGraph ships multi-master replication in the same binary, inside a 5 million triple cap. Blazegraph documents quorum replication in the GPL tree: HAJournalServer elects a leader through ZooKeeper and commits only when a majority agrees. RDFox runs leaderless replicas over a shared file-sequence directory. A commit on one replica becomes visible on the others after they notice it, so the copies are eventually consistent. MarkLogic Server fails a forest over to a local-disk replica or a shared-disk host, and copies journals to another cluster for disaster recovery. The developer licence includes both. Production use needs a paid licence. Read-only HDT files are easy to copy to as many servers as you like. MillenniumDB is a single process, and neither the wiki nor the source describes a replica.

"Free" means very different things.

Jena, QLever, the HDT libraries, Eclipse RDF4J, Oxigraph and sparq give you everything. sparq is MIT, with no paid edition, and the 0.1.6 release is still experimental. MillenniumDB is GPL-2.0, with no paid edition, and the README says it is not production ready. Virtuoso gives you a full single-server engine under GPLv2, and Blazegraph publishes the server, the replication cluster and the scale-out code under GPLv2 as well. GraphDB Free is capped at one core and two concurrent queries, and needs a requested licence. AllegroGraph Free holds under 5 million triples with no licence key. Stardog's free tier is a hosted instance capped at 1M edges, and Neptune offers a 30-day trial. RDFox starts only with a time-limited licence key. The published evaluation agreement allows evaluation, and the term is the expiry date on that key. Commercial prices are not published. MarkLogic Server's developer licence includes every feature, including clustering and high availability, for up to 1 TB. The key lasts six months, can be renewed, and is not for production.

AI features cluster in the commercial products.

GraphDB (Talk to Your Graph, an MCP server, vector connectors), Stardog (Voicebox), AllegroGraph (GraphTalker, native vector stores, an MCP server) and Virtuoso Enterprise (OPAL with MCP) are adding LLM tooling quickly. sparq, still experimental and pre-1.0, documents an opt-in natural-language-to-SPARQL loop and vector search, both outside its default build. MillenniumDB, which the README still calls not production ready, stores one-dimensional tensors and searches them with an HNSW index from SPARQL. It does not call a language model. The other open-source engines document none. RDFox 7.7 ships SEMSIM and semantic-index tuple tables for embedding similarity. RDFox Mantix, announced in September 2026, is a separate companion: a language model helps phrase the question, and RDFox computes the answer. MarkLogic Server 12 indexes vectors for approximate nearest-neighbor search and can mix that with full-text and graph queries. The vectors live in documents and template columns. MarkLogic MCP Server is a separate companion. Neptune's vector and GraphRAG features live in Neptune Analytics, which has no SPARQL endpoint.
